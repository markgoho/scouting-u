# Default to uni-theme-first for shared UI shells; local stays the exception

**Status**: accepted

Supersedes the default set by [ADR 0005](0005-local-first-templates-and-css-against-uni-theme.md). ADR 0005's default was: build local in whichever site needs it first, converge into `uni-theme` only on a named trigger. In practice that default flipped every time it was tested — [ADR 0006](0006-layout-mechanics-from-uni-theme-content-styling-stays-local.md) pulled generic layout mechanics into `uni-theme`, and [ADR 0007](0007-adopt-unithemes-timeline-and-req-list-primitives.md) pulled the timeline/req-list card shell in too, both because building locally first just meant re-deriving a shape `uni-theme` should have owned from the start. The rank landing page (#44) needs a hero/preview/facts/resources shell whose MBU counterpart (`badge-landing.html`) already exists — and, unlike ADR 0005's assumption, its CSS (`components/badge-hero.css`, `pages/merit-badge-landing.css`) already lives in `uni-theme`, generic and documented, not something to build locally at all.

Going forward, before building a page-level UI shell locally, check `uni-theme`'s `CONTRACT.md`: if the shape is already documented there as theme-owned, consume it directly from `uni-theme` — no rename, no local duplicate, even if its class names read as belonging to the other site's domain (`CONTRACT.md` already explains, e.g., why `.badge-hero`/`.badge-identity` count as generic vocabulary rather than mbu-specific). Only when `CONTRACT.md` genuinely doesn't cover the shape yet does "genericize it in `uni-theme` first" apply: extract the pattern there, update every consumer's templates to match, and only then build against it — rather than duplicating the CSS locally or reusing an un-genericized, undocumented class from the other site's own local stylesheet. Content genuinely shaped by one domain's own data (rank's leaf/group requirement-tree structure, mbu's guide/`subrequirement_mode` fields) still stays local, per ADR 0005/0006's still-valid carve-out for content-bound styling — the default flips only for structural/presentational shells.

A near-miss on #44 shows why the `CONTRACT.md` check matters: #49 was opened to "genericize" `uni-theme`'s badge-hero/badge-preview/badge-glance/badge-resources/badge-start-cta classes before scouting-u could use them, on the assumption they were mbu-specific. They weren't — `CONTRACT.md` already documented all of them as theme-owned, and every class mbu's live templates emit was already present in `uni-theme`'s CSS, unchanged. #49 closed as a no-op. Check the contract before assuming a rename or extraction is needed.

This doesn't retroactively require migrating UI that's already reusing site-specific classes as-is (e.g. `badge-identity`/`req-card` reuse from #18) — it sets the default for new work. It also reopens ADR 0007's known gap: mbu's own live templates were never migrated to `.timeline`/`.req-list` after that primitive landed. Close that opportunistically when next touching mbu's requirements page, rather than leaving `uni-theme` with a primitive only one sibling actually uses.
